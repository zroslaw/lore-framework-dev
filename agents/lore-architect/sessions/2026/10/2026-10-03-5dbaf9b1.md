# Drafted finalize participant revision design and spec

The user asked lore-architect to run an end-to-end design cycle without asking questions. The
feature makes `/lr:finalize` decide which workspace agents should learn from a session, and
include them. The motivation came from real usage. Sessions drift into another agent's domain.
Users boot the wrong agent, or none at all. A consulted agent never gets the knowledge it should
keep. The user set minimalism as the governing principle (the fewest concepts, data, code, and
instructions, yet extensible), wanted a minimalism reviewer, and asked for the result as separate
design and spec documents, finalized as a draft for later review.

The agent first surveyed the current flow: `finalize.md`, the reflection, merge, and summarize
procedures, `attach.md`, `consult.md`, transcript reflection, the `lr-core discover` output, and
the lifecycle harness. The design's central observation was that finalization is already correct
for any set of active agents; only the set is wrong. So the design adds a single unnumbered section
to `finalize.md`, "Before Phase 1 — Revise the participants", which acts only through the existing
attach and boot procedures:
- It picks candidates from the workspace routing map.
- It adds an agent only for durable knowledge squarely in that agent's role.
- It re-designates the host when the booted agent owns none of the session's knowledge.
- It prints an Operation Notice before applying any change.

The design adds no new terms, data, code, or flags. Its one honest redefinition is the
"finalization host".

The work ran through three TriLens rounds of cold Sonnet reviewers. Minimalism was a lens in every
round. Round 1 drew a BLOCK from the failure-modes lens on confidentiality. It was resolved with a
rule that fails closed and uses existing repo descriptions, rather than a new visibility field. The
same round also caught a stop rule that would have dropped a booted agent's normal finalize.
Round 2's executor walkthrough found that treating the printed notice as a record of attachment
broke interrupted runs. That rule was cut, and a re-run now re-evaluates from attach confirmations.
Round 3 caught the stop-rule defect returning in a new form, a failed attach of the would-be host,
even though the design already said revision never stops finalize. It was fixed by falling back to
the booted host. All rounds' dispositions are logged in the design doc.

The session ended with two draft documents in the lore-architect workdir:
- `draft-finalize-participant-revision-design.md`: the problem, the design, edge cases E1–E19,
  rejected alternatives, extension points, and the review log.
- `draft-finalize-participant-revision-spec.md`: the exact edits planned for v47 to `finalize.md`,
  three short `summarize.md` definition edits, one `consult.md` sentence, and the finalize
  SKILL.md completion line (which now reports whether revision ran). It also covers release
  bookkeeping, dogfood scenarios, and a lifecycle scenario.

Nothing was implemented in `lore-framework`. Next steps:
1. The user reviews both drafts.
2. A future session implements the spec as v47.
3. That session re-checks the small round-3 fixes, which the three-round ceiling left without a
   fourth review.

## Learning

### lore-architect

- **What mattered:** The finalize participant revision draft is settled in shape and awaiting the
  user's review. It is one pre-Phase-1 section that reuses attach and boot. It never stops a booted
  finalize, and confidentiality fails closed on existing descriptions. Two review lessons came out
  of it:
  - An optional step placed before a mandatory procedure must fall back to baseline at every exit.
  - A notice printed before acting is not proof the action happened.
