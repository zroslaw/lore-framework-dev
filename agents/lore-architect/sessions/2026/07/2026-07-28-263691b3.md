# Moved engine-profile selection out of prose into lr-core

The session opened as an ordinary boot. The user invoked the registered `/lr-lore-architect-agent`
shortcut, preflight reported the repo at version 32 against a framework at 33, and the v33
migration ran — refreshing that very shortcut, which had been pinned to an absolute
`agent-boot.md` path. Boot completed normally. The user then asked a question that turned the
session into something else: had the boot been done as designed, and was there anything to
optimise?

Auditing it honestly turned up two deviations. The smaller one was mine: `register-repo.md`
requires the Claude shortcut to be exactly one line, and the engine profile displays the same
bootstrap wrapped across three lines for readability, so the regenerated shortcut came out wrapped.
That matters more than it looks, because migration 33 classifies a shortcut as `current` only on a
byte-for-byte match, and Claude Code renders a command's description from the file's first line.
The larger one was a framework defect. Boot's Step 0 had the model walk an ordered prose ladder to
pick its engine profile, and one rung read "else if a `~/.codex/` directory exists → codex". This
machine has Codex installed, so a literal executor would have selected the wrong profile for every
Claude Code session. The boot had produced the right answer only because the model consulted its
own belief about which engine it was — evidence the ladder never sanctions.

The fix moved engine selection into `scripts/lr-core` as `detect_engine`, reported as
`data.engine` and consumed at `agent-boot.md` Step 2, with signals ordered override, env,
process ancestry, framework-root containment, then an explicitly `assumed` default. Ancestry
matches the program name rather than any substring of the command line, so a shell sourcing
`~/.claude/shell-snapshots/…` does not read as Claude Code and Cursor's application process does
not read as Cursor when another engine is running in its terminal. `detect_teammate` was
refactored onto a shared ancestry walk, the bootstrap was unwrapped in all three profiles with the
rule stated canonically in `register-repo.md`, and both fixes got tests. Removing the
`--no-teammate-check` instruction from boot fell out of the same change: the flag could no longer
be decided before the call that determines the engine, and the verdict is treated identically
either way.

Two plot twists. The first was a concurrent session: another lore-architect was working the same
workspace throughout, committing and finalizing repeatedly, and at one point its `git add` swept
this session's uncommitted `docs/engines/cursor.md` edits into a commit titled "Cursor: run merge
via Task subagents" and pushed them. Nothing was lost, but work deliberately held back as ungated
went to `origin/main` on someone else's schedule. The second came from the test suite. Two
pre-existing failures looked like rot; only one was. `test_session_archive` had genuinely pinned a
framework version, but the first fix was still wrong — the archive's value is caller-supplied and
the test was asserting `setdefault()` preserves it, so only the stats assertion should read the
live VERSION. The `test_lrb` failure was not rot at all: it asserts no real launchd plist exists,
and it fails here because a Lore Beings Keeper genuinely is installed and running on this machine.
That assertion was left alone, and the discovery corrected a lore-context line describing the
launchd install as still pending.

A `/lr:trilens-loop` round with fixes off produced three reviewer verdicts —
SHIP-WITH-FIXES, SHIP-WITH-FIXES, and BLOCK — across roughly fifteen findings. Two independent
lenses converged on the same defect: `lr-core`'s own docstring still said "read the six steps"
after the insert made them seven. A cold reviewer also found what removing the bad rung had cost:
Codex blocks `ps` and installs under `~/.codex`, so a Codex session against a worktree or dev
checkout now matches nothing and silently lands on the claude profile. Seven findings were fixed
in two passes — the step count, the Codex blind spot (made legible rather than papered over, with
`--engine codex` documented at the point of use), a single-line clause in `/lr:check` #18,
Cursor's teammate gate reworded from an order to a description, the two colliding "Step 2"
references, a self-identification hint in the timeout instruction, and containment now comparing
both logical and resolved paths so a symlinked Cursor plugin dir still matches.

It landed deliberately unshipped. VERSION stays at 33 on the user's explicit instruction, so no
migration, release notes, or manifest bumps were written, and the real-engine lifecycle suite —
the gate this class of change requires — was not run. Unit suites are green: 61 tests in
`test_lr_core`, 6 in the shortcut contract, and the rest of the stdlib suites. Everything except
the already-pushed `cursor.md` remains uncommitted in `lore-framework` and in
`lore-framework-dev/tests`, since finalize's phase 4 stages `agents/` only.

Open threads: eight smaller review findings were accepted as known gaps rather than fixed, among
them unmatched Windows binary names, unvalidated Cursor IDE-chat ancestry, a missing `/lr:doctor`
entry for a wrong or assumed profile, and the absence of any live-engine test that boot actually
reads and acts on `data.engine`. The v34 question is the real one: without a version bump the
single-line shortcut fix has no delivery path, because repos already stamped at 33 never re-run
migration 33. Whether to move the remaining changes onto a branch before the parallel session
commits them is also still open.
