# Made lifecycle and TriLens pre-ship gates on request

The session opened as a question about process rather than code. The user asked what the current
Lore Framework release delivery pipeline actually is, and what a request to "implement something and
deliver it" would concretely expand into. The architect answered from boot context: the two-repo
split, then the ordered sequence — place the change in a layer, implement, run the deterministic
tests, dogfood onto the workspace, run the lifecycle suite, run `/lr:trilens-loop` to convergence,
do the version-ship chores, re-audit the release notes, tag and push, finalize. Three standing rules
were named alongside it: the empirical gates run before the tag, a gate certifies one specific tree
state, and every gate ends as passed, waived, or did not run.

A short follow-up asked whether the quality benchmark was part of that. It was not, and confirming
why surfaced the current state of `tests/quality/`: it measures lore utilization rather than
procedure fidelity, it has always been run-on-request, and its v2 catalog is still uncommitted with
two probes showing a ceiling effect. That answer set up the real subject of the session.

The user then made a policy decision. Running the lifecycle suite and the TriLens loop by default
had repeatedly slowed development and consumed tokens fast, so both were to become optional and
by-request. The user also specified that when TriLens is requested it belongs after the dogfooding
step. The architect raised one concern before acting — this is the same disposition that produced
v40, which shipped without its gates and carried five defects to users — and proposed keeping the
change honest rather than silent: flip the default, but preserve the three-disposition record so
that `did not run` is written into the ship record and said out loud rather than quietly omitted.
The user confirmed, and the work was written into `role.md`, `lore-context.md`, and a new topic,
`feedback-pre-ship-gates-on-request.md`.

Two things went sideways during the edit and are worth recording. The scripted line-index
replacement used to rewrite the long role bullets produced nested bold markup, which silently
corrupts markdown, and a cross-reference reading "same reasoning as the gate above" in a bullet that
sits before its referent. Both needed a second pass. Separately, before finalizing, a completeness
check the architect's own lore demands — enumerate every site that *states* a rule, not just the one
being edited — turned up a genuinely useful negative result: no plugin-layer artifact asserts these
gates as mandatory. The policy lives entirely in agent lore, so changing it needs no VERSION bump,
no manifest bump, and no release.

The session landed with the policy in force and finalized. Merge integrated both reflections, added
the grep verification to the gate-policy topic, created a topic for the scripted-edit failure modes,
and took the opportunity to bring `lore-context.md` back under its v1 budget — from roughly 10,127
to 9,957 estimated tokens — by demoting five details into topics that already carried them. No
framework code or docs were touched, so no gates were required or run for this change.

Open threads are unchanged from before the session: the quality benchmark's v2 catalog is still
uncommitted with two probes needing task-framing rework, and the question of whether quality should
become a real gate for lore-touching releases was raised and deliberately left undecided.

### lore-architect

- **What mattered:** The pre-ship gate policy has no plugin-layer home — verified by grepping
  `lore-framework/docs/`, `skills/`, and `README.md`, which document `/lr:trilens-loop` only as an
