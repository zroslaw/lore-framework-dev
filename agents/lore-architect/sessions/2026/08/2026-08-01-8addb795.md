# Mapped lore improvement directions

The session opened as an exploration of the lore-architect's knowledge base: its size, session history, topic graph, topic sizes, and hubs. The user requested visual proof-of-concepts, resulting in a small core graph and a complete graph of 216 topics and 1,517 directed references. The discussion established that Lore's storage is physically flat but conceptually a linked graph with summary-topic entry points.

The user examined the consequences of that structure: oversized topics, densely connected references, and untyped relationships. The session proposed treating size thresholds as review signals, splitting by independently useful questions rather than arbitrary chunks, and keeping compact overview topics that map to detail. It also proposed lightweight, human-readable relationship labels such as canonical rule, implementation, rationale, supersedes, and related, so future retrieval can follow the relation suited to the task rather than expanding indiscriminately.

The conversation then considered OpenCode as a possible future engine. Its skill discovery, subagent, non-interactive CLI, and MCP capabilities make a capability probe plausible, but the work was deliberately parked pending evidence about subagent semantics, memory conventions, and lifecycle behavior.

The user identified three framework-improvement directions: team governance for publishing finalized lore into shared repositories, an adopter-oriented curation of the command surface, and a clearer worktree lifecycle. Reflection and merge preserved them as new lore topics and linked them into the backlog, command, team-knowledge, worktree, and boot-context guidance. The proposed worktree rule is that dirty state is allowed only while actively owned; parking requires a WIP commit or explicit handoff, and a Git-derived audit should surface stale, merged, or unowned trees.

The session ended with these directions recorded but not implemented as framework changes. OpenCode remains parked; the next design work should begin with the shared-lore contribution lifecycle, then command-surface curation and the worktree audit/lifecycle specification.
