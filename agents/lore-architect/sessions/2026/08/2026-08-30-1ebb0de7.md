# Drafted v44 skill announcements and fixed absolute paths in committed shortcuts

The session opened from a usability complaint rather than a design goal. The user had been
exercising the command surface and noticed that `/lr:workspace-init` and `/lr:workspace-status`
"just silently start to do smth on the background" — transparent to their author, opaque to anyone
else. The proposal was that every skill should first say what it is about to do, and why. What
settled the shape was reframing those lines as onboarding material rather than status output: read
in sequence, they teach the framework's vocabulary without a separate tutorial.

The design converged through several corrections, each of which overturned an initial proposal from
the architect. A shared announcement doc that all 33 skills would point at was rejected in favour of
authoring each announcement in its own skill's doc, with only the *rule* shared in
`conventions.md` — the anti-duplication reflex had been applied to content that was never
duplicated. A mechanical formatting rule (always bold what the skill does to your files) was
rejected as verbose and mis-targeted, since a fixed slot makes several announcements end on a limp
"nothing is changed" while the genuinely surprising thing goes unmarked. Naming subagents "helpers"
for the sake of generality was rejected outright: the audience is engineers who already know the
word. Announcements were also required to distinguish a **lore agent repo** from the ordinary source
repos a workspace holds alongside them.

Implementation covered all 33 skills, which turned out not to mean 33 documents: two skills have no
companion doc and carry their section in `SKILL.md`, the two `df-*` skills live under `df/`, and
`register-repo.md` backs four skills, so its Step 0 branches on the invoked operation. Inserting a
`## Step 0 — Announce` into `agent-boot.md` collided with an existing `Step 0 — Framework root`. The
user asked why not simply renumber; grepping first answered it — renumbering meant roughly thirty
edits across ten files, including a shipped historical migration and the very paragraph that exists
to prevent step-number confusion, whereas renaming cost six. That same grep caught all three engine
profiles citing boot's "Step 0" for framework-root self-location, references that would otherwise
have broken silently while still reading plausibly.

Late in the session the user raised a suspected bug in the shortcut-registration check, involving
absolute versus relative paths, and stated the underlying rule directly: anything committed to a
workspace or lore agent repo must carry relative paths. It reproduced immediately. Generated
per-agent shortcuts embedded an absolute agent directory, so a cloned workspace received shortcuts
pointing at the author's filesystem. The second-order failure proved more interesting than the
first: because `workspace-status` identifies registration by comparing that embedded path, a cloned
workspace reported *every agent as unregistered* — the shortcut sitting in git while the diagnostic
insisted it was missing, routing the user toward a fix for a problem they did not have.

The fix separated one overloaded placeholder into two, `<agent-dir>` for runtime arguments that are
never committed and a new `<agent-dir-rel>` for committed paths, then updated the three engine
profiles, `register-repo.md`, `check.md`, and the scanner, which now accepts both forms so a
workspace mid-migration reports correctly either way. A migration regenerates affected shortcuts
rather than patching their paths, since a shortcut old enough to carry an absolute agent directory
usually carries other retired forms — this very workspace's `lr-tax-advisor-agent.md` also held an
absolute `agent-boot.md` path that `/lr:check` had been rejecting unnoticed. Six new tests were
proven red against the `lr--v1.43.0` tag and green against HEAD; the full suite of 588 passed.

Two process notes outlasted the work itself. The architect's own `lore-context.md` claimed v41 was
current when the repository stood at v43, tagged and pushed — caught only by reading git before
branching, and a near-miss that would have meant rebuilding an already-shipped version. And during a
user-invoked `/simplify` run, the architect named its four cleanup agents `*-lens`, borrowing TriLens
vocabulary for a built-in skill's fan-out; the user asked whether TriLens had been run, which it had
not. Both gates remain deliberately unrun, and v44 stays an uncommitted draft in its worktree at the
user's direction, to be extended in a later session.

## Learning

### lore-architect

- **What mattered:** Separate a shared *rule* from per-site *text* — 33 announcements sharing a shape
  share no string, so single-canonical-source did not apply and a shared file would have added a read
  at execution time for nothing. A cross-reference by step number survives a rename pointing at the
  wrong thing, so grep for citations before renumbering and prefer citing sections by name; measuring
  found 30 edits versus 6. A committed absolute path publishes local configuration as shared
  configuration, and its sharper form is that a checker comparing that value misreports *absence* —
  making a diagnostic lie about a different thing than the one that broke. A fast-moving scalar in a
  slow-moving summary is a stale read waiting to happen: `lore-context.md` said v41 while the repo
  was at v43. Reserve `lens` / `round` / `converged` for `/lr:trilens-loop`, because vocabulary
  leakage corrupts the gate-disposition record as effectively as a wrong entry.
- **Lore changes:** Created `lore/skill-announcement-convention.md`,
  `lore/per-site-authoring-is-not-duplication.md`,
  `lore/committed-artifacts-carry-relative-paths.md`,
  `lore/step-number-cross-references-fail-silently.md`,
  `lore/dont-borrow-gate-vocabulary-for-non-gates.md`. The version-staleness reflection was
  deliberately *not* made a standalone topic — merge folded it into
  `lore/lore-context-shape-discipline.md` as a corollary of the shape rule and lazily migrated that
  legacy file to v1 frontmatter. `lore/single-canonical-source-discipline.md` was updated to record
  the scope limit the session found. `lore-context.md` was materially revised: the Versioning line
  now reads v43 and is explicitly labelled *last known, not current*, applying the session's own
  lesson rather than merely filing it; v44 is recorded as an unshipped draft with its worktree path.
- **Not merged:** None. All six reflection topics were integrated and their files removed.
- **Issues:** The merge subagent's structured handoff was never received — it surfaced only as an
  idle notification. Merge completion was therefore confirmed by direct filesystem inspection
  (reflections consumed, new topics read, diffs reviewed) rather than from its own report, so the
  **Lore changes** list above is derived from `git status` and the diffs, not from the agent's
  account of its work. The integration itself verified as sound. Separately, three of the four
  `/simplify` cleanup agents were stopped by the user before reporting; only the simplification
  agent returned findings, so reuse, efficiency, and altitude coverage did not run. Neither
  pre-ship gate ran for the v44 draft: `/lr:trilens-loop` **did not run**, the lifecycle suite
  **did not run**. The deterministic suite did run — 588 tests green.
