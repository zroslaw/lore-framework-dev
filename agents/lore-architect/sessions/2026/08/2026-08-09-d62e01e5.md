# Prepared Lore Framework v36 for local review

The session opened with a design discussion about making Lore cheaper and easier for an agent to use. The user defined grooming as an iterative practice: reduce context footprint, move important knowledge closer to the navigation path, split oversized topics when useful, improve the taxonomy graph, and remove AI slop without losing durable facts. That led to a concrete three-kind model—one Lore context, recursive Lore areas, and leaf Lore topics—with compact frontmatter that can reconstruct both a detailed taxonomy and a boot-sized map without an LLM census.

The design was implemented as v36 across the framework and development worktrees. The framework gained Lore v1 parsing and validation, compact and detailed maps, bounded grooming worksets, gradual merge adoption, backward-compatible coverage accounting, a `/lr:groom` skill, standardized boot and attach footprint reports, conservative update publication, and a modest split of the former `lr-core` monolith into focused modules. Existing Lore remains untouched by migration 36; adoption is lazy or explicitly requested.

Review repeatedly changed the candidate for the better. Third-party feedback exposed hidden conservative references in mapped topics, invalid-UTF-8 failure behavior, duplicate findings, frontmatter whitespace traps, and missing Git-dirty output. Three TriLens rounds then found update no-clobber and pre-push race gaps, invalid Codex subagent arguments, attach engine propagation and reporting errors, a Codex worktree boot blind spot, an unenforced legacy context ceiling, misleading compact-map wording, and Markdown links with optional titles. Every reported finding was applied and covered deterministically, although the three-round cap meant there was no fourth cold-review attestation.

Release preparation produced 315 passing non-real-engine tests, including 46 focused Lore v1 contracts and a 109-test `lr-core`/Lore subset. The real 220-file Lore Architect corpus mapped successfully and selected a 29,946-token workset under the 30,000-token cap. The canonical regular quality matrix was usable partial: Claude/Haiku showed +50.0-point behavior uplift, Cursor/Composer 2.5 +66.7, and Codex/gpt-5.4-mini +66.3 with one treatment probe timeout and no judge failures. Real-engine lifecycle tests were deliberately not run at the user's direction. The matrix ran against frozen but uncommitted worktrees, so its summary recorded the base `HEAD` SHAs rather than identifying the tested v36 diff; the reporting lore now requires a commit or dirty-state fingerprint for future candidate evidence.

The work landed as local, clean release-candidate commits `1cda4cd` in `lore-framework` and `9f164e9` in `lore-framework-dev`, both on `codex/lore-v1-implementation` and one commit ahead of their upstreams. Nothing was tagged, merged to production, or pushed, preserving the user's review-first constraint. The next session should review those commits and the handoff, optionally rerun the single Codex quality timeout, run lifecycle coverage or record an explicit waiver, then tag and push only after approval.
