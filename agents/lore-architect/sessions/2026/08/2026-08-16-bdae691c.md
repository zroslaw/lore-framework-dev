# Restructured the public README around storage, collaboration, and scale

The session opened as ordinary documentation work: the user wanted to continue improving
`lore-framework/README.md`, starting with the section then titled "Lore technical anatomy." The
brief was specific and arrived in pieces — rename the section to something like "How we store
lore," state plainly that Lore lives in Markdown files rather than in a knowledge base or vector
store, and say that Lore Agents instead rely on what AI coding agents already do well: exploring
and reading their own underlying documents. The decomposition story followed: knowledge broken into
Lore topics, each one small piece; topics referencing each other into a knowledge graph; and a
taxonomy over them as a structured map. `lore-advocate` was attached early, since public copy is its
domain and product truth is the host's.

The section was rewritten as "How Lore is stored," leading with the storage stance before the file
list, and the closing mechanics were merged into a single paragraph so the section did not grow. Two
further sections followed on the user's direction. "Agents working together" covered the case where
a task spans domains — `/lr:recall`, `/lr:consult`, and `/lr:attach` presented in order of weight,
closing on the property that makes the model distinctive: at finalization each agent reflects from
its own perspective, so all learn from the shared session but each learns only what belongs to its
role. "At workspace scale" then made the user's central point, that the most powerful configuration
is a large workspace holding multiple domains, multiple agent repos, and the source code of adjacent
systems, where agents work on top of the real repos and summon each other's expertise as tasks cross
boundaries.

A polish pass followed. Both new sections were converted from dense prose into bold-led bullets with
a single closing paragraph for the payoff, commands were highlighted at their point of use, a light
dot-separated contents line was added after the intro, and nine hyperlinks into `docs/` were woven in
where each concept is first explained. Three smaller defects were fixed along the way: an inverted
sentence in the workspace-scale section that had software areas shining rather than the agents, an
em-dash style inconsistency inherited from an earlier revision, and a sentence duplicated between the
Engine syntax and Skills sections. The result was committed and pushed as `cb0c4e1`; no version bump
was involved, so none of the ship disciplines applied.

The session's plot twist was environmental rather than editorial. Every slash command invoked here —
`/lr:attach`, then `/lr:finalize` — carried a `SKILL.md` base directory pointing at a per-session
plugin snapshot stamped `VERSION` 31, while boot had resolved the installed marketplace root at v40.
This is the topology already recorded in lore, but the first recorded occurrence was benign: the doc
in question was byte-identical between snapshot and live tree. This time a `diff` of the two
`attach.md` files showed a materially obsolete procedure in the snapshot — the pre-v36 `lr-core`
layout, no `--engine` pass-through, no guest boot-map step, and a superseded report shape. Following
it would have executed a v31-shaped attach silently. The v40 root was used throughout and the
divergence was disclosed to the user at each occurrence.

Finalization ran with both agents active. One further environmental detail surfaced during the
commit review: `lore-framework-dev/lore-repo.md` carried an uncommitted 39→40 version-stamp edit
predating this session, which the `agents/`-scoped staging correctly left alone. The architect's
merge also promoted the snapshot topic into the Claude engine-capabilities hub, exactly as that
topic's own Status section had instructed on a second occurrence, and filed the still-undecided
point-of-use guardrail as a backlog item rather than leaving it as an orphaned note.

Open threads are small. The guardrail against acting on a stale per-session snapshot has a backlog
entry but no chosen site — the candidates are a version-consistency line in the skill self-location
preamble, or an `lr-core` check comparing the invoking skill's root against the booted root. The
backlog's standing "README skill table refresh" item was checked against the touched README and
found already satisfied. And per the standing rule in `positioning-triad-differentiation.md`, the
competitive landscape has not been re-surveyed since 2026-07-20, which is due before the next
positioning-sensitive publication built on this README.
