# Diagnosed self-inflicted lore-repo divergence and specced v46 sync hardening

The session opened with the user describing, in loose terms, a recurring frustration: running many
concurrent sessions against the same workspace left lore repos in a state where new agents could not
pull fresh knowledge. Their working hypothesis was that uncommitted files anywhere in a repo blocked
the pull, and they asked for a crisp problem definition before any solution work — explicitly
requesting deep investigation first.

Investigation established that the hypothesis was wrong in a way that mattered. Run against real
fixture repos rather than read from documentation, `git pull --ff-only` proved file-granular: dirty
tracked files, untracked files, and even staged changes at unrelated paths all fast-forward cleanly
with local edits preserved. Only three states block it, and only one — divergence between a local
unpushed commit and an advanced remote — is permanent. Reading the shipped v45 code then showed the
framework manufactures that state itself, through three separate paths: `finalize.md` Phase 4 stages
`git add agents/` and pushes without fetching, `resolve-conflicts.md` abandons a local commit after
three retries, and `update.md` refuses to push precisely when a branch is already ahead. None of it
was visible, because `repo_scan.py` computes no ahead/behind for agent repos. The framework already
owned the correct publication pattern — narrow staging, post-commit verification, preconditions
re-resolved before push — and applied it only to its two rarest operations.

At the user's request four cold reviewers explored the solution space. That round killed the
session's most attractive idea: a "sidecar publish" using git plumbing to commit onto the fetched
remote head without touching the working tree. It demonstrably worked from a hopeless repo, but
three of four reviewers independently established that it leaves the working tree permanently unable
to fast-forward, and that `git commit -- <paths>` already supplies the one property the plumbing was
built for. The design collapsed to something duller and better: narrow pathspec staging, commit
verification, and a bounded merge-and-retry push.

A full implementation specification followed, then three review rounds against it — the loop's hard
ceiling — producing 43 findings and five BLOCK verdicts in total. Each round found something real.
Round one: conflicts can touch paths outside the write-set whenever a stranded commit sits on the
branch. Round two: a pathspec commit inside an unfinished merge fails fatally with `HEAD` unchanged,
which the spec misread as "nothing to publish" — a repo left mid-merge would have swallowed every
later publication silently and forever; and the design's central "never fail silently" promise was
unenforceable for the unattended Being daemon, whose stranded run is recorded as a clean one. Round
three found that round two's own fix had reintroduced the ratchet it was written to prevent, through
a rollback exception that was not merely wrong but never technically necessary.

The loop did not converge, and the session treated that as diagnostic rather than as a reason for a
fourth round. Classified by origin, the findings showed a stable core no lens ever attacked and a
churning elaboration around it — the signature of a document that has outgrown what prose review can
certify. The response was to tier the work: Tier A ships the four changes no reviewer ever touched,
including bare divergence detection, which then measures how often the problem actually occurs;
Tier B, the cure itself, gets one deep unconstrained cold reviewer before implementation; Tier C —
the marker, the daemon surfacing, the conflict classification, which generated most of the findings
in every round — is deferred until Tier A's data says whether it is worth building at all.

The user set the session's communication style to plain, dialogue and follow partway through, and
the working rhythm shifted to short turns with the user steering between them. Several corrections
landed on the assistant's own work rather than on the framework: the sidecar demo had tested only
the operation and not the state it left behind, and the stranded-publish marker had been designed as
a verdict when it should have been a hint that self-clears. Both became named lore topics.

## Learning

### lore-architect

- **What mattered:** `git pull --ff-only` is file-granular, not repo-granular — only divergence, a
  modified tracked file an incoming commit also touches, or an untracked collision block it, and
  only divergence is permanent; lore repos go stale because the framework manufactures divergence
  through finalize Phase 4, `resolve-conflicts.md`, and `update.md`, while `repo_scan.py` leaves it
  invisible to `/lr:check`. `git pull --ff-only --autostash` exits 0 on a real content collision
  while writing conflict markers into the file, so no automatic path may resolve a conflict by
  discarding. A demo of a write operation is not evidence until it runs the next ordinary read —
  publish then pull, commit then boot — which is what invalidated the sidecar-publish design.
