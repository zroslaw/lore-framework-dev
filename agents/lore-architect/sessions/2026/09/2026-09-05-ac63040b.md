# Recorded the macOS Keeper login-item name-and-icon technique

The session was a knowledge-transfer one rather than a build one. A separate piece of work,
carried out earlier the same day on this machine (MacBookPro16,1, Intel, macOS 26.6.2), had chased
down why the Being Keeper LaunchAgent shows up in System Settings as `python3.14` with a blank
document icon, and had found a mechanism that actually fixes it. That finding arrived here as a
brief with the instruction to absorb it as lore in the architect's own voice, file the upstream
framework proposal, and finalize — the empirical work itself was already done and was not repeated.

The substance came down to one thing the brief called the key insight and the merge kept as the
canonical fact: the displayed **name** and the displayed **icon** in that pane come from two
unrelated sources. The name is the filename of `ProgramArguments[0]`; the icon is a per-file
custom icon — a `com.apple.ResourceFork` xattr holding an `.icns` plus the `kIsCustomIcon` Finder
flag — set through `-[NSWorkspace setIcon:forFile:options:]`. Fixing one does not fix the other.
The sharpest supporting result was negative: macOS never resolves a `Contents/MacOS/…` path back
to its enclosing bundle's `CFBundleIconFile`, so wrapping the daemon in an `.app` buys the name and
never the icon. That was settled by a control test against a known-good comparable (Turbo Boost
Switcher, which renders its icon only because its plist runs `/usr/bin/open` on the bundle, making
Background Task Management record the bundle path). Two other candidate mechanisms were ruled out
with reasons — `AssociatedBundleIdentifiers` needs a matching Team ID that ad-hoc signing cannot
supply, and the `/usr/bin/open` route exits immediately under `KeepAlive` and loses the plist's
`EnvironmentVariables`, which the Keeper needs for `LRB_HOME` and a `PATH` carrying `claude`.

Before writing any of it down, the claims about `lrb.py` were re-verified against the shipped code
rather than taken from the brief: `cmd_install` does write `sys.executable` into
`ProgramArguments[0]` at `lrb.py:1511`, and `_daemon_status` at `lrb.py:1621` does only
`os.kill(pid, 0)` with a comment saying it deliberately skips executable-name identity checks — so
a wrapper genuinely does not break status detection. Evidence grade was recorded as "ran it, plus
read the shipped code."

The upstream ask was filed in the two places the architect uses for such things: a detailed bullet
in `lore/framework-improvements-backlog.md` under § Autonomous Agents / Lore Beings, and ranked
item **B11** in `workdir/what-to-improve.md`, the standing prioritized action view. The proposal is
that `lrb install` lay down a small named-and-iconed wrapper and point `ProgramArguments[0]` at it,
so every Lore Beings user gets a legible background item instead of an interpreter name. Its
shipping blocker is recorded honestly: the strip-signature-then-set-icon step is verified on Intel
only, and arm64 mandates a signature, so it is **unverified** on Apple Silicon rather than assumed
to work.

Two transferable lessons came out beyond the macOS specifics. One is a new cost axis on the
cheapest-first gate ordering: every LaunchAgent plist edit makes Background Task Management
re-evaluate the login item and raise an admin password prompt, so six or seven
`bootout`/`bootstrap` cycles charged the user six or seven interruptions — a "free" probe against
live OS state can be the most expensive step in the session, and the mechanism that finally worked
needed zero reloads. The other is the generalized diagnostic: before fixing a rendered artifact,
ask how many independent sources compose it and confirm each attribute separately, and probe a
known-good comparable rather than enumerating mechanisms against the broken case.

Where it landed: three new lore topics, four existing ones cross-linked, `lore-beings-design.md`
lazily migrated to v1 while it was being edited, and both improvement stores updated. During
finalization the merge subagent flagged that the hand-written B11 entry restated mechanism detail
now canonical in lore; that was trimmed to a pointer rather than left as a second copy. One open
item carried forward unchanged: `lore-context.md` was already over the 10,000-token v1 target
before this session (10,422) and is 10,557 after, so a demotion pass is owed.

## Learning

### lore-architect

- **What mattered:** A macOS login item's displayed name and icon come from two unrelated sources — the filename of `ProgramArguments[0]` and a per-file custom-icon xattr on that same file — and macOS never resolves a `Contents/MacOS/…` path back to an enclosing `.app`'s `CFBundleIconFile`, so the per-file custom icon is the only one of three candidate mechanisms usable for a daemon (verified on Intel only; arm64's mandatory signature makes strip-then-icon unverified there and a shipping blocker). Generalized: ask how many independent sources compose a rendered artifact before fixing it, and probe a known-good comparable rather than enumerating mechanisms against the broken case. New cost axis on cheapest-first gate ordering — each LaunchAgent plist edit re-triggers Background Task Management and prompts the user for an admin password, so rank mechanisms by *user* cost, validate on a copy, and prefer ones touching only a file attribute over ones that re-register with the OS.
