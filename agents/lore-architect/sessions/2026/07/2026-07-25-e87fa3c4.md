# Shipped /lr:trilens-loop as framework v30

The session opened with the user wanting to stop retyping a prompt they used often: review a set of changes from three different perspectives, each perspective handled by a separate subagent so the reviewers do not inherit the bias of the session that wrote the code, then triage the feedback, fix what deserves fixing, and repeat the whole cycle until nothing meaningful comes back. They asked whether it should be a command or a skill, wanted it engine-independent, and wanted a single entry point rather than several so the skill catalog would not bloat. The first useful thing the agent could contribute was recognition rather than design: the flow already existed as accumulated lore (`parallel-reviewer-fanout-pattern.md`, hardened across the v11–v28 ships), the user had independently articulated the same flow in a June design dialogue, and it sat in the backlog as "Reusable multi-lens review skill." The work was therefore a promotion of existing operating knowledge into a plugin capability, not a greenfield feature.

Design settled over several short exchanges. It ships as a skill, since "command" is only an engine's surface for one; core plugin layer rather than the DF module, because the pattern is domain-agnostic; one optional free-text argument and no flags, matching `/lr:recall [hint]` and working identically on every engine. The user made two decisions that overrode the agent's initial leanings: free text may amend anything including the safety rails (the agent had proposed keeping reviewer independence and the round cap fixed), and native engine subagents only, no headless shell-out workarounds. Naming converged on `trilens-loop` after the user asked for something reflecting both the three perspectives and the cycle; the agent flagged that "lense" is a misspelling and the user took the correct form.

The Cursor question consumed real time and changed the shape of the feature. The framework's Cursor engine profile forbade relying on native subagents, which would have made the skill impossible there. Investigation showed this was the agent's own epistemic caution rather than a discovered limitation — the Cursor probe notes contained no mention of subagents at all, because the conservative serial fallback had been sufficient for every skill that existed when the profile was written. Cursor's own documentation confirmed subagents shipped in 2.4 with a `Task` tool, CLI included. That produced the session's most useful conceptual output: in every prior fan-out site the subagent is an optimization, so serial host-side execution reaches the same answer more slowly, but here independence *is* the deliverable, so the same fallback clause is feature-destroying rather than merely slower. The engine profile gained a carve-out for that class of procedure, and the principle was named as its own lore topic.

The skill was then run against its own changes, which was both the point and the best evidence. Four rounds converged 14 → 6 → 1 → 0 findings, twenty applied and one declined. It caught a genuine self-contradiction between the free-text rule and the never-self-review rule; a factual error where the agent had cited a Cursor changelog date that no official source supports; a fix-the-fixes miss where the same correction landed in two files and missed a third; and a lifecycle scenario-number collision that only the whole-diff round could see, because the colliding files were unmodified and never entered a lens-scoped reviewer's field of view. The most instructive failure was the agent's own: it spawned the first round of reviewers with names, which on Claude Code makes them Agent-Teams teammates that do not auto-return their reports, so all three went idle and the round had to be re-run unnamed — a trap its own lore had recorded since v18 but which lived in agent lore rather than in the engine profile an executor reads at the moment of spawning. That fact was moved into the Claude binding.

Two things then went sideways. After the lifecycle suite passed 3/3 across claude, codex and cursor, the agent noticed Codex's cheapest tier under-reporting and tightened the doc twice more — edits that fell outside both gates it had just passed. The recheck intended to cover them was destroyed when macOS revoked Documents-folder access mid-run, which first hung one scenario to its full timeout and then broke fixture setup entirely. The agent misdiagnosed that twice (file permissions, then session cwd drift) before identifying it as a TCC permission reset, and stopped rather than flailing. The user resolved the permission issue out-of-band; a long token-limit wait was bridged with re-armed background timers after `lr-wait` turned out to be capped at roughly thirty minutes by the MCP idle timeout and to hold its single-request lock after being killed.

Where it landed: framework v30 is committed, tagged `lr--v1.30.0` at `11ec0df`, and pushed, with `VERSION` at 30 and all four version-bearing manifests at `1.30.0`. The dev repo carries lifecycle scenarios 28–29, the design record, and the version-history entry. The honest gap is that the verified 3/3 result belongs to the pre-tightening artifact; on repeat runs afterwards Codex at `gpt-5.4-mini` returned `FINDINGS: none` on one of two scenarios over a file with two planted defects, which reads as weak-model variance rather than a procedure defect since the same doc passes elsewhere. The user chose to ship with that documented rather than iterate further, and the release notes and version history both record it.

Next steps are small and already filed. The Codex fidelity gap is disclosed rather than fixed, so a future ship's gate should confirm it. The merge phase surfaced a real framework bug now in the backlog: boot Step 0's engine-detection rules check for a `~/.codex/` directory before checking the parent process, so on a machine with several engines installed a literal reader selects the wrong profile — both agents this session picked correctly on parent-process evidence rather than by following the written rules, which is precisely the prose-not-code risk the multi-engine work is meant to retire. The Cursor `Task` free-text-versus-named-definition question also remains unmeasured, and the merge noted that v29's features had never received lore topics, a gap it closed while integrating this session's.
