# Re-reviewed the shipped v37 and shipped v38 as a correctness pass

The session opened with the user asking for a TriLens loop over v37 — already shipped, tagged, and
pushed — with instructions to fix whatever it found, ship the result as v38, skip the lifecycle and
quality suites, and finalize. The complication was that v37 had already been reviewed twice, most
recently by a three-round, nine-lens loop, so twelve lenses were spent before this session began.
Repeating any of them would have bought thinking the release had already been given. The first real
move was therefore an inventory of the lenses already used, drawn from the version-history topic and
the August session records, followed by a deliberate reframing: v37 was no longer a proposal to be
judged but a shipped artifact with an installed base. That reframing chose the round-one lenses —
concurrency and idempotency in a live multi-session workspace, the hostile-reality input surface,
and three-engine parity.

All three of those reviewers died on the account spend limit before reporting, the same failure that
had killed a round during the v37 ship. Per the framework's own rule a silent round is never banked
as clean, so nothing was recorded; when the user lifted the limit, the lenses were re-run. That
sequence sharpened an existing lore rule rather than merely obeying it: the injunction against
retrying an account-level failure is really about retrying into an *unchanged cause*, and once
someone outside the loop removes the cause, the retry is an ordinary re-run that does not count
against the three-round ceiling.

The re-run found real defects that nine prior lenses had not. Two independent implementations of one
rule had drifted apart — the Python scanner that reports on a workspace and the bash script that
acts on it disagreed about which repositories are declared, so a repository could be cloned
correctly and then reported missing forever with no error anywhere. A repeated `repos:` block
silently discarded the first block's URLs on the Python side only; a trailing ` # comment` was
stripped by the awk parser and baked into the URL by the Python one; a leading-dot directory name
was accepted by both and then skipped by every later pass. Alongside those, `workspace-push` staged
framework-managed paths explicitly and then ran a bare `git commit`, which commits the whole index —
so anything a concurrent session had staged rode along, a routine occurrence in a workspace that
runs unattended sessions. A new finding, S16, was added for a detached workspace HEAD: the scanner
had recorded the state from the beginning and no finding had ever read it, and it is the one root
state that makes the git section go quiet rather than loud, since a detached HEAD has no upstream
and the ahead/behind findings therefore cannot fire.

The plot twist was recursive, and it repeated. Round two, aimed at the fixes rather than the
release, found two defects introduced by round one's own fixes — a blank line that broke the
findings table so the newly added S16 row would not render at all, and a paragraph made unreachable
by a precondition that already handled the case — plus two overstated claims in the new prose. Both
claims were the author's own: that the two parsers now agreed, which a commented URL falsified, and
that a pathspec commit closed the race, which it does not, because `git commit -- <path>` takes the
path's working-tree content rather than freezing what was staged. Both were corrected rather than
defended. Round three, run against a frozen commit after a reviewer rightly objected that the tree
had moved under it mid-review, then found defects in round two's fixes in turn: a re-read
instruction that could not be executed because no step captured the baseline it told the executor to
compare against, and — sharpest, given the release's whole theme — the new directory-name rules left
unstated in the very document that finding S13 sends users to. The release had fixed one instance of
a rule duplicated across sites and created another one in prose.

Version 38 shipped as framework commit `0435186`, tag `lr--v1.38.0`, pushed to origin, with all four
version-bearing manifests at `1.38.0` and release notes but no migration. The deterministic suite
went from 387 tests to 414, and each new test was verified red against the `lr--v1.37.0` tag in a
temporary worktree before the fix and green after, so the coverage is load-bearing rather than
decorative. The honest limit on the ship record is that the loop ended at its three-round ceiling
rather than on a clean round: every finding raised was applied, but round three's own fixes are
unreviewed and no reviewer returned a clean verdict on the shipped tree. The lifecycle and quality
suites were waived by explicit user direction and not run, so the release makes no claim about
model-execution fidelity on any engine — both facts are recorded in the release notes and the
version history rather than left implicit.

Open threads: a fourth round would review the round-three fixes, which the ceiling forbids within
this loop but which a later session could run cheaply against the tag. Several findings were
deliberately accepted rather than applied and remain open — case-insensitive directory-name
collisions on macOS, where two declared URLs differing only in case collide on disk without
triggering the collision finding; the absence of any per-target lock in the clone path; and a
`SIGKILL`-interrupted clone that later runs treat as healthy because `origin` is configured before
the object transfer completes. The workspace still has not been dogfooded onto v38, and
`lore-framework-dev` and `lore-agents` still stamp version 37 while `lore-chronicler` stamps 34.
